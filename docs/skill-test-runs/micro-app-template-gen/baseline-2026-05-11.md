## Scenario

Subagent attempts to author a micro-app template for "homeowner files an insurance claim" given only the spec + stub SKILL.md (no references/, no question bank, no examples).

The subagent role-played as an insurance-industry SME. The brief was: model the homeowner's side of filing a claim with their carrier — they apply, attach evidence, await a decision, and accept or react. They are a holder/applicant, not an issuer.

## Gaps Identified

These are the specific points where I struggled, invented an answer, or could not decide between options. Each is a target for the references/ files.

1. **Schema SAIDs for held credentials are entirely fabricated.** I used `EPlaceholderHomeownerPolicySchemaSAID0000000` for `homeowner_policy` and `EPlaceholderClaimDecisionSchemaSAID000000000` for the apply-target schema. The spec says these are "imports SAIDs that the Ecosystem Viewer matches against other templates' issued[].schema_said," but I have no carrier template to import from. The schema validator accepts any 44-char string. The skill needs a clear policy for placeholder SAIDs: a recognizable prefix, a TBD marker, a sentinel value, or a separate "unresolved-imports" list in metadata.

2. **The `apply` verb's "schema_said_referenced" target is a guess.** When the homeowner sends `apply` via IPEX, what schema SAID do they reference? My instinct was "the schema of the credential they want issued back to them (claim decision)." But this could equally be: (a) the policy schema they're claiming against, (b) a hypothetical claim-application schema that doesn't exist in this template, or (c) a carrier-defined IntakeRequest schema. The spec says `schema_said_referenced` exists on the exchange object but doesn't say *which* schema for the `apply` verb. I picked (a)-ish (claim decision) by analogy to the spec's regulator example where carrier's apply references the license schema.

3. **`idempotency_key_expression` syntax is invented.** I wrote `hash(payload.policy_said + payload.incident_date + payload.incident_type + payload.incident_description)`. UEL/1.0 has no published grammar in the spec. Does `hash()` exist as a builtin? Is `+` string concatenation? Should the expression coerce types? I assumed JavaScript-ish syntax because the spec's own examples (e.g., `state + [{ ... }]`, `state.filter(p => ...)`, `state.exists(...)`) read as JavaScript. The skill needs a one-page UEL/1.0 cheat sheet listing accepted builtins (`hash`, `now`, `duration`, `merge`, lambda syntax, `.exists()`, `.filter()`, `.map()`, comparison ops).

4. **`payload_mapping` is technically a UEL expression but the spec gives it as a free-form template-literal-looking string.** The spec example uses `"{ said: event.credential.said, jurisdiction: event.credential.attributes.jurisdiction, ... }"`. Is that a UEL object literal, a JS template literal, or something else? I followed the spec's pattern verbatim, but a real implementer would need a grammar. Same problem for `fold_expression`, `lens_template`, and `expression` on rules.

5. **`lens_template` syntax is unspecified.** Spec example: `"Active Policies — {state.length} in force"`. My equivalent: `"My Claims ({state.length} total, {state.filter(c => c.status == 'submitted' || ...).length} open)"`. The string-interpolation rules are not defined: is `{...}` UEL? Are pipes (`|aid8`, `|date`, `|money`) allowed inside? I used pipes only in the `display.columns[].display_template` because that's where the spec showed them; but `lens_template` may or may not support them. Invented.

6. **No guidance on aggregate event-type naming.** I used past-tense snake_case verbs (`claim_filed`, `evidence_attached`, `decision_received`, `claim_denied`), modeled on the spec's `license_received` example. But event types are also referenced from `projections[].source_events[]`, `reactions[].emissions[].event_type`, and `aggregates[].inception_event_type`. The skill should mandate a single naming convention and document the cross-references.

7. **Reactions to "carrier acknowledged claim" — protocol verb or app-level exn?** When a carrier sends "we received your claim," is that an IPEX `offer`/`agree` against the original `apply`, or a separate exn on `/insurance/note/claim_acknowledged`? I chose the latter (exn notification) because the spec doesn't list "acknowledgment" as an IPEX verb — only apply/offer/agree/grant/admit/spurn. But a more KERI-pure design might use `agree` here. Need a reference doc mapping common conversation patterns (intake ack, info request, partial approval, full grant) to verb+route choices.

8. **Modeling "request for more information" — reaction shape?** When the carrier asks for more evidence, is that (a) an exn notification, (b) an IPEX `offer` with conditions, (c) a `spurn` followed by a new apply, or (d) a brand-new exn on a `/qry/` route? I chose (a) — a notification message. The skill needs a worked-example pattern for "counterparty asks me for more information" because this happens in *every* multi-step bilateral flow.

9. **Aggregate `state_schema` vs `output_schema` on projection — duplication?** My `claim_history` aggregate has a `state_schema` describing `{ claims: [...] }`, and my `my_claims` projection has an `output_schema` describing essentially the same shape (just one level flatter). The spec says aggregates carry folded state and projections fold over events to produce views. In practice for a "list of items" projection, the aggregate and projection look nearly identical. Should the skill recommend "if the projection is just a view of an aggregate, the fold expression is essentially identity and the output_schema mirrors a slice of state_schema"? Or should aggregates be omitted when a projection serves the same role? Invented the answer (kept both, with the projection adding `last_event_at`).

10. **`time_bound.duration` format is invented.** I used ISO-8601 durations: `P7D`, `P60D`. The spec's example is `"30 days"` — a natural-language string. Both are valid by the meta-schema (it's just `type: string`). The skill needs to pick one and stick to it; mixed templates will not be machine-comparable.

11. **`temporal_preconditions` semantics are murky.** I split predicates between `state_preconditions` (state checks, e.g. "no duplicate open claim") and `temporal_preconditions` (time checks, e.g. "incident within policy term"). But `incident_within_policy_term` reads attribute values from a held credential — it's arguably state, not time. The line between state/auth/temporal is fuzzy. The skill should give 4-5 worked examples of each precondition kind so authors can copy-classify.

12. **`role.keri_infrastructure` defaults for `individual`.** The spec says "individual often has only mailbox" — so I set `mailbox: true` and the rest false. But could a wealthy homeowner run their own witness pool? The spec uses "often." This is a fine default but I want it to be a default the skill applies automatically, not invented per author. Add `kind → keri_infrastructure` defaults table to the references.

13. **Rule purpose `auth_precondition` vs business reality.** My `holds_active_homeowner_policy` rule is marked `purpose: auth_precondition`. But "authorization" in KERI usually means cryptographic — proving you hold a key. Here it means "the actor's wallet must currently hold a credential." Are those the same thing in this vocabulary? The schema accepts either reading; semantic ambiguity remains.

14. **No issued credentials → no `value_flow`, no `edges`, no schema files.** I'm 90% confident this is the right modeling: the homeowner files (apply), attaches evidence (notification), withdraws (spurn), and admits (admit) — none of which is the homeowner *issuing* an ACDC. But there's a defensible alternative reading where the homeowner issues a `ClaimApplication` credential of their own that the carrier holds, and the carrier responds by issuing a `ClaimDecision` credential back. The spec doesn't prescribe which design. I picked the "thinner" design. The skill needs a decision framework: when is something a credential vs. a payload-only exn? My heuristic was "if the artifact needs to be independently presentable to a third party (court, regulator, secondary market), it's a credential; if it's transient back-and-forth, it's an exn payload." But this is my own invention.

15. **`reactions[].trigger.credential_held_id` mismatch on decision grant.** I set the reaction trigger's `credential_held_id: "homeowner_policy"` for the "claim decision granted" reaction, but that's wrong-feeling — the credential being granted is a *new* credential (claim decision), not the existing policy. However, the spec's reaction trigger only allows referencing `credential_held_id` that's in `credentials.held[]`, and I haven't added "claim_decision" to held. If I had, that would be an "import" that this micro-app expects the carrier to issue, which is more correct. **This is a real gap** — I cheated by reusing the policy credential id, and a careful reviewer would catch it. The right modeling is to add a second held credential `claim_decision` with its own (placeholder) expected_schema_said. The schema xref validator accepts my version because the id resolves, but the semantic is wrong.

16. **No `withdraw_claim` analog in the workflow steps.** My workflow doesn't have a step for "homeowner withdraws while waiting." The `withdraw_claim` command exists but is orphaned from the workflow definition. The spec allows commands to exist outside workflows (they can be invoked directly from the UI), but the skill should prompt: "for each command, decide if it belongs in a workflow step or is standalone."

17. **Verifier roles for credentials we don't issue.** Not applicable here (we issue nothing), but if I had issued something, I'd have had to invent `verifier_roles` — and the spec doesn't tell me what verifier_roles do in practice or how to scope them. The skill needs a one-liner on intent: are verifier_roles informational (whom the issuer expects to verify) or normative (who *may* verify)?

## Rationalization Patterns

- **"The spec example does this so I'll copy it"** — used for `idempotency_key_expression`, `lens_template`, `payload_mapping`, `time_bound.duration`. Worked for getting valid JSON, but the resulting expressions are not analyzable by anything until UEL/1.0 is specified.
- **"The meta-schema accepts it"** — used for placeholder SAIDs, ambiguous routes, the role-name deviation. The validator says OK so I declared OK. But the meta-schema is permissive on strings; it cannot catch semantic nonsense.
- **"The homeowner doesn't issue, therefore no schemas"** — used to justify an empty `schemas/` directory. This is the *thinnest* defensible reading. A maximalist reading would have me issue a `ClaimApplication` credential of my own. I picked thin without surfacing the tradeoff.
- **"I'll mirror the carrier-license example"** — used in mapping the homeowner's apply→grant flow onto the spec's carrier-license example. Worked for shape but means I never actually thought through whether the spec's vocabulary fits homeowner claims any better than license applications.
- **"Past-tense snake_case is conventional"** — used for event types. Convention not specified anywhere; I picked the pattern from `license_received` and replicated.
- **"I'll invent rule ids that read English"** — used throughout. `holds_active_homeowner_policy`, `no_duplicate_open_claim_for_incident`. Worked for readability but the spec gives no naming convention for rule ids, which means cross-template alignment by name will be ad-hoc.

## Decisions for the Skill Build

Based on what tripped me up, the references/ + SKILL.md prose must address these concretely:

1. **`references/uel-1.0-cheat-sheet.md`** — a one-page grammar reference. Builtins (`hash`, `now`, `duration`, `merge`), lambda syntax, collection methods (`.exists`, `.filter`, `.map`, `.length`), operators, string interpolation in templates, the pipe syntax inside `display_template` and (TBD) `lens_template`. Without this, every `expression`, `payload_mapping`, and `fold_expression` is just a free-text string the meta-schema can't analyze.

2. **`references/placeholder-sads-policy.md`** — how to write `expected_schema_said` when the issuer template doesn't exist yet. Recommend a single sentinel format (e.g. `EUNRESOLVED_<credential_id>_______________________` padded to 44 chars) AND a `metadata.json.unresolved_imports` array listing each. Without this, every author invents their own marker.

3. **`references/exchange-shape-decision-tree.md`** — a flowchart-style reference for "is this a `credential` exchange, a `message` exchange, or a `null` (internal) emission?" plus "which IPEX verb fires when?" — including the not-obvious cases like "carrier acknowledges receipt" (notification message vs. agree verb), "carrier requests more info" (notification vs. spurn-and-reapply vs. exn query), "homeowner withdraws" (spurn vs. notification).

4. **`references/credential-vs-payload-heuristic.md`** — when do you model an artifact as a held/issued credential, vs. an exn payload? Three-question filter: (a) does it need to be independently presentable later? (b) does it confer authority or attest a fact? (c) does it have a lifecycle? Yes-to-any-of-these → credential. All no → payload. Worked example: claim evidence (payload), claim application (could go either way — show both designs and pick), claim decision (credential).

5. **`references/event-and-rule-naming.md`** — pick conventions and enforce them. Event types: `<noun>_<past-tense-verb>` snake_case (`claim_filed`, not `fileClaim` or `ClaimFiledEvent`). Rule ids: `<verb>_<noun_phrase>` snake_case for predicates (`holds_active_policy`, `claim_is_open`), `<noun>` for prose (`good_faith_reporting`, `duty_to_mitigate`). Document the choice; have the skill lint deviations.

6. **`references/precondition-classification.md`** — auth/state/temporal precondition is murky. Provide 6-8 worked examples each:
   - auth: "principal holds an active credential of type X" — about identity and capability.
   - state: "no duplicate row in aggregate Y" — about local fold state.
   - temporal: "current time is within window W" or "now - X < D" — about clock comparisons.
   Plus mixed-case discussion: "principal holds X" with a lifecycle filter is auth; "incident_date within X's effective term" reads attributes of held credentials but compares dates → temporal.

7. **`references/skeleton.json`** — a fully filled-in minimal-but-complete template (5-6 primitives each), heavily commented inline (well, JSON has no comments — but described in a companion file). Authors copy-paste then mutate. Saves 30 minutes of "what's the shape of a workflow_trigger" lookups.

8. **`references/role-defaults-and-conventions.md`** — for each `role.kind`, the typical `keri_infrastructure` defaults and the role-id naming pattern. Explicitly: `individual` → `{ witness_pool: false, watcher_network: false, mailbox: true, acdc_registry: false }`. `organization` → all true. Plus a glossary mapping "homeowner" → `policyholder_individual` (role-naming convention if strictly applied) with the note "deviation acceptable if industry-standard term."

9. **`references/aggregate-vs-projection-design.md`** — when aggregates and projections overlap (which is most of the time for "list of items I care about"). Recommend: aggregates are *log-derived* state (the canonical history), projections are *consumer-facing views* (per-user filters, columns, transformations). Even when their schemas look similar, both belong; the projection adds access control and display hints that don't belong on the aggregate. Worked example showing what's "in" each.

10. **`references/adversarial-checklist-prompts.md`** — the spec's Appendix B is good but reads as a list. Turn it into a prompt-able interrogation: "Walk this template through 7 attack vectors. For each: (a) Lies (impostor presents forged credential) → does our auth_precondition rule actually verify the cryptographic substrate? (b) Revocation race ... (c) Concurrent commands ..." with a question for each that the skill must ask before declaring done.

11. **SKILL.md expansion**: add explicit "you must" / "you must not" rules:
    - You must not skip Step 9 (rules) — even a single rule.
    - You must surface placeholder SAIDs in metadata.unresolved_imports if any are present.
    - You must validate xref AND validate AND saidify-verify before declaring done (not just one).
    - You must commit the empty `schemas/` if the role issues no credentials (so the directory layout is consistent across templates).
    - For each command, ask "is this orphan from any workflow? if so, is that intentional?"

12. **One worked example end-to-end as a reference** (T20 in the task list) — a single fully-working homeowner-claim template (or this baseline's, edited and pristine) checked into `examples/` for authors to crib from. Real-world this is what cut my time in half on subsequent runs.
